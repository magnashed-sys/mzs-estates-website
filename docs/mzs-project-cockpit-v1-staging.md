# MZS Group — Project Cockpit V1

Status: **READY FOR ISOLATED STAGING ACCEPTANCE ONLY**.
No owner approval for a Production migration or merge has been given.

## Objective

Let an authorized MZS Group administrator manage a project's catalog
information, individual sale/investment/rental/financing offerings, published
editorial updates, and private downloadable project documentation in one
place, without rewriting Next.js page components for every content update.

## Delivered Phase 2 scope

1. `/admin/projects/[id]`: Project Cockpit for each existing project.
2. Admin Overview: project title, subtitle, location and **dashboard-only**
   local hero image path. Slug and project status cannot be changed here.
3. Offerings: edit title and summary; create additional offering types as
   `draft` (database allows at most one of each type per project), publish
   with explicit confirmation, and only return offerings to draft if no
   members hold offering grants. **Never** auto-assign new opportunities.
4. Project content: plain-text blocks in existing `project_content` table.
   New blocks save as drafts; publication is a separate explicit action.
   Ordered content is rendered in a new "Project updates" section on each
   private project presentation, after the existing presentation.
   Never render HTML supplied in the editor.
5. Private project documents: new `mzs_project_documents` metadata table and
   `mzs-private-project-documents` **non-public** Storage bucket.
   PDFs, common images, DOCX and XLSX, maximum 20 MiB.
   Private uploads start as drafts. Explicit per-document publication.
   Audience selected when uploading: all members assigned project access or
   only members with an explicit grant for one selected *active* offering.
   Signed links expire after **60 seconds**. Link sharing during the
   valid period is still possible.
6. Existing private presentation, image galleries, sale/investment-specific
   components, rental configuration, booking/calendar workflows and project
   access-saving APIs are preserved; newly published text/documents are
   complementary, not replacements.
7. Admin project list and Project Access page now link to Project Cockpit.
   Project Cockpit links back to individual Relationship 360 dossiers and
   the existing verified project permissions editor.

## Technical implementation

- Next.js route: `app/admin/projects/[id]/page.tsx`
- Editors: `OfferingManager.tsx`, `ContentManager.tsx`,
  `DocumentManager.tsx`
- New client renderer: `app/private/projects/[slug]/ProjectResources.tsx`
- Supporting models/CSS and links in admin pages
- Additive SQL: `supabase/migrations/20261016_project_cockpit_private_documents_v1.sql`

### Data security

- Admin guard checks authenticated Supabase user `profiles.role=admin`
  and `is_active=true`.
- Supabase RLS enforces admin mutations on existing projects, offerings
  and content. Member users can read only their active assigned projects
  and offerings.
- Document metadata RLS requires publication, active client, active
  project access; an offering-scoped file requires a distinct grant for
  that offering and its active status.
- Storage `storage.objects` SELECT policy checks the same published
  metadata, inheriting its RLS rules. INSERT/DELETE are admin-only.
- File paths are UUID-scoped, generated by the browser, validated at DB
  insert. Metadata trigger prevents referencing an offering belonging
  to a different project.
- The document upload is a two-stage operation (private Storage upload
  then metadata insert); failed inserts trigger best-effort cleanup.
  File deletion first unpublishes metadata, removes Storage object,
  then removes its metadata record. A rare partial failure may require
  admin reconciliation; the UI reports an unconfirmed result.
- Client links are never public bucket links. Authorized sessions must
  request signed short-lived URLs.
- Every preview-specific new Admin route checks the known isolated
  Staging Supabase URL before loading personal, company or project data.
- Do not copy staging secrets into source, chat or document descriptions.

## Stage-based acceptance plan

Before logging in, open the current branch Preview's
`/api/staging/readiness` and verify `readyForProjectCockpitTesting=true`.
If false, **do not sign in** or upload files on that deployment.

1. Sign in as the MZS **Staging administrator**. Go to
   Admin → Projects & access → Open Project Cockpit.
2. Choose a synthetic test project. Verify its overview, offerings,
   content, documents and client access tabs.
3. Rename a synthetic project's title or subtitle; save and reload.
   Check private dashboard catalog changes with the client test account.
4. Add a draft text block; check it is **not** visible to the client.
   Publish the block, log in as the assigned test client, and check
   the new "Project updates" section. Unpublish afterward.
5. On a test project without an offering type, create a draft offering.
   Verify it is not automatically granted to existing members.
6. Upload a **fictional, non-confidential** test PDF. Verify it remains
   a draft; publish it for one specific offering, verify the appropriate
   client can open it, and verify a different member cannot.
7. Unpublish and delete the test PDF. Verify the bucket and metadata
   contain no unexpected orphaned records.
8. Ensure original booking calendars, investment presentations,
   project access and Relationship 360 still function without regressions.
9. Confirm baseline staging permissions remain unchanged; do not expose
   customer documents, credentials or live client data in Staging.
